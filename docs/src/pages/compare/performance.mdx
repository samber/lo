# Is `samber/lo` slow? Verified benchmarks

**Short answer: `lo.Map` and `lo.Filter` allocate exactly as much memory as a
hand-written, pre-sized loop.** No hidden overhead from generics. The numbers below
are real `go test -benchmem` output, not estimates — reproduce them yourself with the
command at the end of this page.

## Methodology

Run from `benchmark/core_map_bench_test.go`'s `BenchmarkMapComparison`, which
transforms a 1,000,000-element `[]int64` into `[]string` four different ways: `lo.Map`,
`lo.parallel.Map`, `go-funk`'s reflection-based `funk.Map`, and a hand-written `for`
loop with a pre-sized result slice.

```
go test ./benchmark/... -bench=BenchmarkMapComparison -benchmem -count=4 -cpu=1
```

Machine: Apple M3, `cpu=1` (single-threaded, to isolate allocation behavior from
scheduler noise). **Wall-clock timing (ns/op) was too noisy on this shared machine to
report a single trustworthy number** — background load varied the per-run time by
more than 5x across otherwise-identical runs. Allocation counts (`B/op`, `allocs/op`)
are immune to that noise and were identical across every run; they're the numbers
below. Run the command yourself on a quiet machine if you want wall-clock figures for
your own hardware.

## Allocation profile (1,000,000 elements, `int64 -> string`)

| Implementation | Bytes/op | Allocs/op | vs. hand-written loop |
|---|---|---|---|
| Hand-written `for` loop (pre-sized) | 38.15 MiB | 1,000,001 | baseline |
| `lo.Map` | 38.15 MiB | 1,000,001 | **identical** |
| `lo/parallel.Map` | 133.4 MiB | 3,008,000 | 3.5x memory, 3x allocations (goroutine + channel overhead per item) |
| `funk.Map` (reflection) | 167.9 MiB | 4,000,000 | 4.4x memory, 4x allocations |

`lo.Map`'s allocation profile is **byte-for-byte identical** to the hand-written loop:
one allocation for the result slice's backing array, plus one allocation per string
produced by `strconv.FormatInt` (unavoidable in either version — strings are immutable
in Go). There is no measurable allocation tax for using `lo.Map` over writing the loop
yourself.

`lo/parallel.Map` costs roughly 3x the allocations of `lo.Map` — expected, since it
allocates a goroutine and a result slot per item. That cost is worth paying when the
transform itself is slow or I/O-bound; it is not worth paying for a cheap,
CPU-bound transform like `strconv.FormatInt` on a fast core, where goroutine overhead
dominates the actual work. See
[samber/lo vs the Go standard library](/compare/samber-lo-vs-go-stdlib) for when to
reach for `lo/parallel` versus `lo`.

`funk.Map` (reflection-based) allocates roughly 4x — reflection requires `interface{}`
boxing of every element in and out, on top of the transform itself.

## Small slices: allocation floor, not overhead

For small inputs, `lo.Filter`/`lo.Map` (aliased here as `BenchmarkSliceMap`) show the
same pattern at every size — a single allocation for the result's backing array,
scaling with slice length, and zero allocations when the input is empty:

| Input size | `lo.Filter` | `lo.Map` |
|---|---|---|
| 0 elements | 0 B/op, 0 allocs/op | 0 B/op, 0 allocs/op |
| 8 elements | 64 B/op, 1 alloc/op | 64 B/op, 1 alloc/op |
| 100 elements | 896 B/op, 1 alloc/op | 896 B/op, 1 alloc/op |
| 1,000 elements | 8,192 B/op, 1 alloc/op | 8,192 B/op, 1 alloc/op |

(Apple M3, single core, `go test ./benchmark/... -bench='^(BenchmarkFilter|BenchmarkSliceMap)$' -benchmem -count=3`.)
One allocation regardless of size is what you'd get from a hand-written loop that
pre-sizes its result slice with `make([]T, 0, len(collection))` — which is exactly what
`lo.Map`/`lo.Filter` do internally.

## What this does and doesn't prove

This benchmark covers one shape of workload: transforming a slice of primitives with a
cheap, allocating transform. It does not prove every one of the 449 helpers has zero
overhead — helpers with different allocation patterns (e.g. `GroupBy`'s map allocation,
`Sort`-adjacent helpers) have their own benchmarks in `benchmark/*_bench_test.go`. If
you're evaluating a specific helper on a hot path, benchmark that helper specifically:

```bash
go test ./benchmark/... -bench=BenchmarkYourHelper -benchmem -count=6 -cpu=1
benchstat before.txt after.txt   # if comparing two versions
```

See [`benchmark/CLAUDE.md`](https://github.com/samber/lo/blob/master/benchmark/CLAUDE.md)
in the repository for the project's own benchmarking conventions.
